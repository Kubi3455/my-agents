Last month I let an agent write and run its own cleanup script for a batch of scraped PDFs, and its idea of "cleaning up" was a shutil.rmtree on a path two levels higher than the one I'd actually pointed it at. Nothing of mine was lost, because the whole thing was running inside a throwaway VM I'd already treated as disposable. Lucky, this time. It was still a sharp reminder of why AI agent code execution sandboxes exist: code-execution tools don't ask permission before they act, and a model that's 95% right the other 5% of the time is still running on your infrastructure.

If you've wired a run_python or execute_shell tool into an agent and just let it rip against the host machine, you already know this pain. Maybe it hasn't bitten you yet. It will, usually the day a prompt injection slips in through a scraped web page or a tool result the model trusted a little too much.

Here's what I actually dug into: how AI agent code execution sandboxes from E2B, Modal, and Daytona isolate that code, where the isolation boundaries genuinely differ, and which one I'd reach for depending on what you're building.

Why AI Agent Code Execution Sandboxes Matter Right Now

The threat model here isn't exotic. An agent with a code-execution tool can, in principle, read your environment variables, write to disk, open a socket, or shell out to anything the runtime allows. Most of the time that's fine, because most of the time the model is doing exactly what you asked. Usually it is. The problem shows up when it isn't: a hallucinated "fix," or a prompt injection buried in a document the agent was asked to summarize, that quietly tells it to exfiltrate credentials or open a reverse shell.

This is a different failure mode from the control-flow bugs I've written about before, where an agent loops on the wrong branch or never reaches a terminal state. A stuck ReAct-style control loop wastes tokens. Unsandboxed code execution can touch things outside the conversation entirely, which is a much worse class of problem.

So the question isn't "should I sandbox," it's "how much isolation does this workload actually need, and what does that cost me in latency and complexity." That's where E2B, Modal, and Daytona start looking genuinely different from each other, instead of three logos on the same comparison chart.

Firecracker, gVisor, and Plain Containers: What the Boundary Actually Buys You

A standard Docker container shares the host kernel. That's fine for isolating one well-behaved service from another, but a shared kernel means a container-escape bug in the kernel itself is a sandbox-escape bug for you too. For agent-generated code, where you can't fully predict what's going to run, that's a thinner wall than I'd want between a model and my infrastructure.

Firecracker, which AWS open-sourced and E2B builds on, takes a different approach: every sandbox gets its own guest kernel inside a hardware-virtualized microVM. It's a real VM boundary, just a very lightweight one. gVisor, which Modal uses by default, does something else again: it's a kernel written in user-space Go that sits between your process and the real Linux kernel, intercepting every syscall before it reaches the host. Fly.io's own comparison of the two frames it well: different isolation strategies, defending against different failure modes, at different performance cost. No second kernel, but also no syscall gets through unexamined.

Neither is strictly "more secure" in the abstract. Firecracker's hardware virtualization defends against a wider class of kernel bugs because there's a full extra kernel in the way. gVisor's syscall interception is lighter-weight and (in Modal's case) is also the only runtime that supports attaching a GPU, since hardware passthrough and a separate guest kernel don't mix well. Pick based on what you're running, not on which word sounds scarier.

E2B: Firecracker microVMs, Built for Agents From the Start

E2B's own open-source runtime repo describes the setup bluntly: one Firecracker microVM per sandbox, each in its own cgroup and network namespace, with a per-sandbox nftables firewall that can allow- or deny-list outbound domains. That last part matters more than it sounds. A sandbox that can run arbitrary code but can't reach arbitrary hosts closes off a whole category of exfiltration attempts before they start.

The SDK is deliberately thin:

# pip install e2b
from e2b import Sandbox

sandbox = Sandbox.create(timeout=120)  # seconds; needs E2B_API_KEY in env
result = sandbox.commands.run("python3 -c \"print(2 + 2)\"")
print(result.stdout)  # "4"
sandbox.kill()

Per E2B's own lifecycle documentation, a sandbox can run up to an hour on the Hobby plan or 24 hours on Pro before it's forcibly killed, and you can pause one mid-run to preserve filesystem and memory state, then resume it later instead of starting cold. That pause/resume model is a genuinely nice fit for anything built around durable agent workflows that need to survive a crash without replaying every tool call from scratch.

Where E2B gets interesting is self-hosting: the same infra repo ships a single-machine deployment called Embed, so you're not locked into their cloud if compliance requires the sandbox to live inside your own network. I wouldn't call that a weekend project to set up, but it's a real option, not a marketing line.

Modal: Pick gVisor or a Full VM, Then Decide if You Need a GPU

Modal's Sandbox API makes the isolation choice explicit instead of hiding it behind a single default. You pass runtime="gvisor" for the lighter, syscall-intercepted container, or runtime="vm" when you need a full Linux kernel, say, because the agent's code needs to run Docker inside the sandbox or mount a FUSE filesystem. Leave it unset and Modal picks for you.

# pip install modal
import modal

app = modal.App.lookup("agent-sandboxes", create_if_missing=True)
sb = modal.Sandbox.create(
    app=app,
    image=modal.Image.debian_slim().pip_install("pandas"),
    runtime="gvisor",
    timeout=10 * 60,       # max sandbox lifetime, seconds
    idle_timeout=60,       # kill if nothing's running for 60s
)
proc = sb.exec("python", "-c", "import pandas; print(pandas.__version__)", timeout=5)
print(proc.stdout.read())
sb.terminate()

Default lifetime is five minutes. That's it. It pushes you to think about timeouts up front instead of discovering them in production. You can stretch that to 24 hours with the timeout parameter, and past that Modal's own docs point you at a filesystem snapshot-and-restore pattern rather than one giant sandbox. "Idle" has a specific meaning here too: a sandbox with a command still running, stdin still open, or an active tunnel connection doesn't count as idle, so idle_timeout won't kill it out from under a long-running job.

The GPU angle is the real differentiator against E2B. If your agent's tool call needs to run a model locally inside the sandbox, Modal's gVisor-runtime GPUs are the straightforward path; that's just not a use case E2B or Daytona are built around.

Daytona: The Open-Source Story Got Complicated

Daytona describes itself as a "secure and elastic infrastructure runtime for AI-generated code execution and agent workflows," and for a while it was the open-source name people pointed to when they wanted something they could audit and self-host without a vendor in the loop. That changed in 2026. Checking the repo directly instead of trusting a vendor-comparison post: it's now archived and read-only on GitHub, with the README stating that core development has moved to a private codebase and the public repo will receive no further updates, fixes, or releases.

The existing code is still there, still licensed for you to fork and run, "without support or warranty," in the repo's own words. That's a real option if you're already committed to it. Fair enough. I just wouldn't start a new project on a dependency whose maintainer has publicly stopped maintaining it, however generous the license is on the way out.

Honestly, that's the main reason Daytona drops to third place in this comparison right now, not the isolation technology itself. The frozen repo doesn't document its own sandbox internals with anywhere near the detail E2B's and Modal's docs do, which made it the one tool here I couldn't verify a specific implementation claim for.

Choosing an AI Agent Code Execution Sandbox: Side-by-Side

Running the Same Tool Call Two Different Ways

Say your agent has a generic run_code tool that an LLM calls through a tool-calling agent framework. On E2B, the whole round trip is create, run, read, kill:

from e2b import Sandbox

def run_code_tool(code: str) -> str:
    sandbox = Sandbox.create(timeout=30)
    try:
        result = sandbox.commands.run(f"python3 -c {code!r}")
        return result.stdout or result.stderr
    finally:
        sandbox.kill()

On Modal, you're spinning up (or reusing) an App first, which is a small extra ceremony but gives you Modal's image-building and dependency-pinning machinery for free:

import modal

app = modal.App.lookup("run-code-tool", create_if_missing=True)

def run_code_tool(code: str) -> str:
    sb = modal.Sandbox.create(app=app, timeout=30)
    try:
        proc = sb.exec("python3", "-c", code, timeout=25)
        return proc.stdout.read() or proc.stderr.read()
    finally:
        sb.terminate()

Neither snippet is production-ready. Not even close. You'd want to handle partial output on timeout, and if the tool is called in parallel by the same agent, the same race conditions that show up in parallel tool calling apply here too: two sandboxes writing to a shared result store need the same locking discipline, sandbox or no sandbox.

Pros and Cons, Honestly

Pros of E2B

  • Firecracker isolation per sandbox, documented in the open infra repo rather than taken on faith
  • Pause and resume preserves full state, useful for long-running or crash-prone agent loops
  • Self-hostable if you need the sandbox inside your own network

Cons of E2B

  • No published default timeout number, only maximums; you have to set one explicitly
  • No native GPU story if your tool call needs to run a model

Pros of Modal

  • Explicit choice between gVisor and full-VM isolation per sandbox
  • GPU-backed sandboxes, which neither of the other two is built around
  • Clear idle-vs-active distinction for timeouts, so a long tool call won't get killed mid-run

Cons of Modal

  • Hosted only; there's no self-hosted Modal if that's a hard requirement
  • Default 5-minute lifetime means you'll hit a timeout the first time you forget to set one

Pros of Daytona (For Now)

  • Existing code is still public and licensed to fork and run
  • If you're already deployed on it, nothing breaks today

Cons of Daytona (For Now)

  • Public repo archived; core development moved to a private codebase
  • No further fixes or releases on the open version, by its own README
  • Sandbox internals aren't documented in the same depth as E2B's or Modal's

Common Pitfalls When Sandboxing Agent Code

The pitfall I see most often isn't picking the wrong vendor. It's picking a good sandbox and then undermining it. A few that are easy to miss:

  • Leaving outbound network wide open. Isolation stops the code from touching your host; it doesn't stop the code from phoning home to an attacker's server unless you also restrict egress, the way E2B's nftables allow-list does.
  • No timeout, or a timeout that's too generous. A runaway loop in agent-generated code is common enough that "it'll probably finish" isn't a real plan. Set the tightest timeout the task can tolerate.
  • Reusing one long-lived sandbox across unrelated tool calls. State leaks between calls that should be independent, and one bad call can poison the next one's environment.
  • Trusting sandbox stdout as safe to show the user unfiltered. The sandbox protects your infrastructure, not the end user reading the output. A sandboxed process can still print something it shouldn't.

None of these are exotic. They're just easy to skip when the sandbox itself is already doing the hard part, and it's tempting to assume the hard part was the whole job. Two more worth planning for up front: sandbox creation is just an API call under the hood, and it can throttle you the same way covered in this retry strategy for 429 errors, so don't skip backoff just because the call happens to say "sandbox" instead of "chat completion." And a verbose stdout from a long-running script adds up fast if you're feeding it straight back into the model's context, which is exactly the context bloat problem in a different costume.

Conclusion

If you're building a general-purpose coding agent and don't need GPUs, I'd start with E2B. The Firecracker-per-sandbox model is the clearest documented isolation story of the three, and pause/resume fits naturally with agents that need to survive a crash mid-task. If your tool calls need to run a model inside the sandbox itself, Modal's gVisor-with-GPU option is the one built for that, and the explicit runtime choice is a nice bit of honesty most platforms don't bother with.

Skip Daytona for anything new right now, not because the isolation is bad, but because you can't verify what it is anymore from the one source that would normally tell you. A frozen repo is a fine thing to keep running if you're already on it. It's a strange foundation to build on from scratch in 2026.

Whichever you pick, set a real timeout and an egress allow-list before you ship, not after the first incident teaches you why they exist.

FAQ

Is a Docker container enough to sandbox AI agent code execution?

For low-risk, fully trusted code, often yes. But a standard container shares the host kernel, so a kernel-level escape affects you too. For agent-generated code you can't fully predict, a microVM (E2B's Firecracker) or a syscall-intercepting runtime (Modal's gVisor) closes that gap.

What's the real difference between Firecracker and gVisor?

Firecracker gives each sandbox its own guest kernel inside a hardware-virtualized microVM. gVisor is a userspace kernel that intercepts syscalls from a normal container without a second kernel underneath. Both raise the bar above a plain container; they just raise it in different places.

Can I self-host E2B or Modal instead of using their cloud?

E2B, yes: its open infra repo ships a single-machine self-hosted mode called Embed, on top of full enterprise deployments. Modal is hosted-only; there's no self-hosted version of the Modal platform itself.

Does Daytona still work if I'm already using it?

The public code still runs and is licensed to use, but the GitHub repo is archived and its own README says there will be no further updates or fixes on the open version, since core development moved to a private codebase.

Do I need a GPU sandbox for most agent code-execution tools?

No. Most tool calls, data parsing, API calls, small scripts, don't need one. Reach for a GPU sandbox only when the tool call itself needs to run a model, which is the specific case Modal's gVisor-runtime GPUs are built for.
