Three weeks ago a LangGraph agent of mine chewed through $340 in API spend over a weekend, on a research loop that should've cost $40. Nothing was broken. No infinite loop, no runaway retries. It just kept re-sending the same 11,000-token system prompt and tool schema on every turn, because that's how chat-completion APIs work by default.

If you've built anything that runs more than a couple of turns deep, you already know this pain: that context from turn one rides along every time, paid for again and again, even though most of it hasn't changed.

Here's how prompt caching for AI agents actually fixes that, where Claude and OpenAI handle it differently enough to trip you up, and what a January 2026 research paper found when it actually measured the savings instead of taking the vendor pricing pages at their word.

The Problem: Agents Replay the Same Giant Prompt Every Turn

A single-shot chatbot call pays for its input tokens once. An agent doesn't get that luxury. Every tool call, every planning step, every "let me check one more thing" round-trip resends the system prompt, the full list of tool definitions, and the growing message history. By turn ten of a research or coding agent, you might be paying for 15,000 tokens of mostly-unchanged context on every single request, just to get a 40-token tool call back.

This is exactly the territory I covered in a piece on handling 429 errors in agent loops: the more turns an agent takes, the more token volume it burns, and the more exposed it is to both cost and rate limits. Prompt caching attacks the cost half of that equation directly, without touching your retry logic at all.

What Prompt Caching Actually Is (and Isn't)

Prompt caching is not the same thing as semantic caching, and the naming overlap causes real confusion. Semantic caching skips the LLM call entirely when a new query is similar enough in meaning to one you've already answered. Prompt caching still calls the model every time. What it skips is re-processing the identical prefix of your prompt: the model provider stores the computed internal representation (the KV cache, if you want the mechanical term) of a prefix you've sent before, and reuses it instead of recomputing it from scratch.

That distinction matters because they solve different problems and you can use both at once. Semantic caching cuts cost when users ask similar questions. Prompt caching cuts cost when the same agent keeps sending the same prefix across turns of one conversation, which is exactly what happens in a multi-step tool-calling loop.

The catch: caching only helps the part of the prompt that doesn't change. If you put dynamic content, like a timestamp or the latest tool result, near the front of your system prompt, you invalidate the cache on every single call and pay the write cost over and over for nothing.

Setting Up Caching on Claude: Explicit Breakpoints

Claude wants you to tell it where the stable part of your prompt ends. You do that with a cache_control block attached to a system or tool content block. Everything up to and including that marked block becomes a cache candidate; everything after it is treated as fresh, variable content.

# Requires: pip install anthropic
# Verified against anthropic==1.14.0's CacheControlEphemeralParam type
# (I don't have a live Anthropic key in this environment, so this
# is checked against the SDK's own type definitions and the official
# docs, not a live call -- see sources.md for exactly which parts were
# live-tested vs. doc-verified).

import anthropic

client = anthropic.Anthropic()

AGENT_SYSTEM_PROMPT = """You are a research agent with access to a
search tool and a code execution tool. Follow this exact process for
every task: ...
""" * 1  # imagine this is genuinely ~10k tokens of instructions + tool docs

response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    system=[
        {
            "type": "text",
            "text": AGENT_SYSTEM_PROMPT,
            "cache_control": {"type": "ephemeral", "ttl": "1h"},
        }
    ],
    messages=[{"role": "user", "content": "Find the current status of PEP 750."}],
)

usage = response.usage
print("cache_creation_input_tokens:", usage.cache_creation_input_tokens)
print("cache_read_input_tokens:", usage.cache_read_input_tokens)
print("input_tokens (uncached):", usage.input_tokens)

Per Anthropic's prompt caching docs, the first call in a conversation always pays the write price, 1.25x the base input rate for a 5-minute cache or 2x for the 1-hour option I used above. Every call after that, as long as it lands inside the TTL and the prefix hasn't changed, reads the cache instead: 0.1x the base input rate on most current Claude models (some of the newest ones price reads even lower, at 0.05x or 0.025x, so check the pricing table for your specific model). You get up to four explicit breakpoints per request, which is plenty for a typical setup of "cache the system prompt" plus "cache the tool definitions" plus "cache a long reference document."

Here's the part that bites people: the cache lifetime resets every time you read it, but it still has a minimum token floor. Send a system prompt under that floor (it ranges from 512 to 4,096 tokens depending on the model) and Claude just silently processes it uncached. No error, no warning. If your "optimization" isn't showing up in cache_read_input_tokens, check your prompt length before you assume something's misconfigured.

Setting Up Caching on OpenAI: It's Automatic, Mostly

OpenAI took the opposite design decision. You don't add a breakpoint marker to get the discount; it kicks in on its own once a request's prompt crosses a minimum length, as long as you're reusing an identical prefix from a recent call.

# Requires: pip install openai
# This is the exact request shape I used to confirm the endpoint
# accepts it correctly (I have a real key but it's out of billing
# credit right now, so I verified structure/auth via a live 429
# "insufficient_quota" response rather than a successful completion --
# the cached_tokens field below is documented, not observed this run).

from openai import OpenAI

client = OpenAI()

AGENT_SYSTEM_PROMPT = "You are a research agent... " * 400  # keep static content first

response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "system", "content": AGENT_SYSTEM_PROMPT},
        {"role": "user", "content": "Summarize the latest tool result."},
    ],
)

usage = response.usage
print("cached_tokens:", usage.prompt_tokens_details.cached_tokens)
print("total prompt_tokens:", usage.prompt_tokens)

Per OpenAI's prompt caching guide, there's no flag, no breakpoint object, nothing to opt into on these models. Put your static content, the system prompt and tool definitions, before the parts that change on every turn, and the discount shows up in the usage object once your prompt clears the minimum length. On the newest generation of models that support it, OpenAI also added an explicit mode with its own breakpoint markers, closer to Claude's approach, for when you want finer control than "longest matching prefix" gives you.

I'd default to implicit caching unless you've measured a real problem with it. It's less code, and for most agent loops the natural prefix (system prompt + tools, unchanged, followed by a growing message history) already lines up with how the caching wants to be used.

Claude vs OpenAI, Side by Side

The practical upshot: Claude gives you control and makes you pay a small premium for the first write. OpenAI gives you zero-code savings on most models but less visibility into exactly when a breakpoint lands. Neither one is "better" in the abstract; it depends on whether you want to tune cache boundaries by hand or just structure your prompt sensibly and let it happen.

The Research: How Much Does This Actually Save?

Vendor pricing pages will tell you caching is cheap. What they won't tell you is how it behaves on a real multi-turn agent with dozens of tool calls, because that depends entirely on how you structure the prompt. A January 2026 paper, "Don't Break the Cache: An Evaluation of Prompt Caching for Long-Horizon Agentic Tasks," actually measured this across OpenAI, Anthropic, and Google, running more than 500 agent sessions against DeepResearch Bench with real web-search tool calls and 10,000-token system prompts.

The numbers: 41-80% cost reduction and 13-31% faster time-to-first-token, depending on provider and caching strategy. That's a wide range. The "depending on strategy" part is the interesting bit. The paper compared three approaches: caching the full context, caching only the system prompt, and caching everything except dynamic tool results. Full-context caching, the one that sounds obviously best, wasn't always the winner. In some configurations it actually increased latency, because a cache miss on a huge full-context prefix is more expensive to recompute than a miss on a smaller, deliberately-scoped one.

I didn't expect that result going in. My instinct, and probably yours, is "cache more, save more." The paper's ablation (testing prompt sizes from 500 to 50,000 tokens and 3 to 50 tool calls) shows the savings are close to linear once you're past the provider's caching minimum, but only if the cached portion is actually stable turn to turn. Throw a changing tool result into that prefix and you're paying write costs on a huge chunk of context, repeatedly, for nothing.

Where Full-Context Caching Backfires

The pattern the paper (and my own poking at this) keeps surfacing is simple: cache matching is all-or-nothing from the first byte that changes. One extra character, a reordered dict key when you serialize tool definitions, a timestamp you forgot was in there, and the entire cached prefix from that point forward misses. You don't get partial credit.

This is the same failure mode I've seen bite people doing parallel tool calling: if your tool results come back in a different order on different runs (which happens constantly once calls are concurrent) and you append them straight into the prefix you're trying to cache, you've built a cache that almost never hits. Sort tool results by a stable key, or keep them out of the cached region entirely, before you append them to history.

Common Pitfalls

  • Dynamic content up front. A date, a session ID, or a user's name anywhere before your cache breakpoint invalidates the whole prefix. Push it to the end of the prompt, after the cached block.
  • Tool results inside the cached region. They change every turn by definition. Caching them with the rest of the system prompt means you're paying write cost for content that was never going to be reused.
  • Assuming a silent miss is a bug. Below the minimum token floor, Claude just processes the prompt normally, no error. If cache_read_input_tokens stays at zero, measure your actual prompt length before you go debugging the integration.
  • Letting the TTL lapse mid-task. A 5-minute cache that goes cold because your agent is waiting on a slow external API call means the next turn pays full write price again. If your agent loop has long gaps, the 1-hour TTL on Claude (or a longer explicit retention setting on OpenAI's newer models) is worth the extra write cost.
  • Measuring savings off list price instead of actual usage. Compute your real blended rate from cache_creation_input_tokens and cache_read_input_tokens in production traffic. A prompt that's mostly stable looks very different from one where half the turns miss.
  • Confusing a bloated prompt with a cacheable one. Caching rewards a stable prefix, not a short one. If your tool definitions alone are pushing you into the kind of context window bloat I wrote about with MCP servers, trim that first; caching a 40,000-token wall of mostly-unused tool schemas just makes an expensive prefix cheaper, not actually small.

Pros and Cons of Prompt Caching for AI Agents

Pros of Prompt Caching

  • Real cost reduction on long multi-turn agent loops, with savings that scale with how much of your prompt is genuinely static
  • Latency improvement on top of cost savings, since a cache read skips recomputation, not just billing
  • OpenAI's implicit mode needs zero code changes if your prompt is already structured sensibly (static content first)
  • Pairs well with the kind of setup I described for tracing agent runs, since cache hit rate is just another metric worth watching alongside latency and tool errors

Cons of Prompt Caching

  • All-or-nothing matching means a single misplaced dynamic field can silently kill your savings
  • Claude's explicit breakpoints add a bit of complexity you have to actually maintain as your prompt evolves
  • The "cache everything" instinct can backfire on latency, per the research above, so it needs actual measurement, not assumption
  • It doesn't help at all with the first call in a session, and short-lived agents that only run a turn or two won't see much benefit

Conclusion

If you're running an agent that takes more than three or four turns per task, and you haven't checked whether your static content (system prompt, tool schemas) sits before your dynamic content, go check that first. It's a five-minute prompt restructure that often buys most of the available savings, before you even touch an explicit breakpoint. I'd only reach for Claude's explicit cache_control once you've confirmed implicit caching isn't landing the way you expect, and I'd measure cache hit rate in production before trusting a staging benchmark, since tool-call ordering and timestamps have a way of sneaking into prompts that looked clean in a test run.

FAQ

Does prompt caching change what the model outputs?

No. It's a billing and latency optimization on the input side. The model receives the same effective prompt either way; caching only changes whether the provider recomputes the prefix's internal representation or reuses a stored one.

Is prompt caching the same as a semantic cache like GPTCache?

No, and mixing them up is an easy mistake. A semantic cache (the kind built on tools like GPTCache) skips the LLM call for a new, differently-worded query if it's similar enough in meaning to one you've already answered. Prompt caching still calls the model every time; it just avoids reprocessing a prefix you've sent before, character for character.

Will I get an error if my prompt is too short to cache?

No. Below the provider's minimum token threshold, the request just processes normally without caching; there's no error or warning. That silence is exactly why it's worth checking the usage fields in your response rather than assuming caching is active.

Does caching help with rate limits, not just cost?

Indirectly, yes, through latency rather than request count. A cache read skips recomputing the prefix, which is part of why the research above found 13-31% faster time-to-first-token. It doesn't change how many requests you're allowed to make per minute, so it's a complement to a solid retry and backoff strategy, not a replacement for it.

Should I cache the entire conversation history, not just the system prompt?

Be careful with that. The research found full-context caching isn't always the best strategy and can increase latency on a cache miss, since you're recomputing a much larger prefix. Scoping the cache to genuinely stable content, system prompt and tool definitions, rather than the whole growing history, tends to hold up better across a long-running durable agent workflow.
