I spent a Saturday convinced my local agent had gotten dumber overnight. It had been calling a search tool fine all week, then it just... stopped. No error, no crash, just a model answering from memory, ignoring the three tools I'd registered.

I checked the model, checked the prompt, checked my sanity.

The actual bug was two layers down: the OpenAI-compatible endpoint had quietly dropped my context-length setting, the tool schemas got shoved out of context before the model saw them, and nothing in the response said so.

Ollama tool calling agents don't need LangChain in the loop. If you've wired Ollama into an agent loop, the native /api/chat endpoint has supported OpenAI-shaped function calling since mid-2024, and as of this week it got meaningfully better. You need about forty lines of Python and a clear idea of where it breaks, not a framework.

Here's how Ollama tool calling actually works without LangChain in the loop, the exact agent loop I run, the context-window bug that cost me that Saturday, and which models are worth trusting with a tool in the first place.

What Ollama Tool Calling Actually Looks Like on the Wire

Skip the framework abstraction for a second and look at the raw request. You POST to /api/chat with a tools array, and each tool is the same JSON Schema shape OpenAI popularized: a type: "function", a name, a description, and a parameters schema.

import requests

TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "Get the current weather for a city",
            "parameters": {
                "type": "object",
                "properties": {"city": {"type": "string"}},
                "required": ["city"],
            },
        },
    }
]

resp = requests.post(
    "http://localhost:11434/api/chat",
    json={
        "model": "qwen3",
        "messages": [{"role": "user", "content": "What's the weather in Istanbul?"}],
        "tools": TOOLS,
        "stream": False,
    },
    timeout=30,
)
print(resp.json()["message"])

If the model decides to call get_weather, the response's message has a tool_calls array, and each entry looks like {"function": {"name": "get_weather", "arguments": {"city": "Istanbul"}}}. The detail that trips people coming from the raw OpenAI API: arguments is already a parsed dict, not a JSON string. Call json.loads() on it like you're used to and you'll get a TypeError for your trouble. I did exactly that the first time, and the traceback was about as unhelpful as you'd expect for "you tried to parse something that wasn't a string."

Building Ollama Tool Calling Agents (No LangChain, No AutoGen)

A tool-calling agent is just a loop: ask the model, check if it wants a tool, run the tool, hand the result back, repeat until it answers in plain text. That's the whole pattern LangChain wraps in an abstraction layer. Written out directly, it's not much code:

import requests

def get_weather(city: str) -> str:
    return f"14°C and cloudy in {city}"  # swap for a real API call

AVAILABLE_FUNCTIONS = {"get_weather": get_weather}

def run_agent(prompt: str, model: str = "qwen3") -> str:
    messages = [{"role": "user", "content": prompt}]

    resp = requests.post(
        "http://localhost:11434/api/chat",
        json={"model": model, "messages": messages, "tools": TOOLS, "stream": False},
        timeout=30,
    )
    resp.raise_for_status()
    message = resp.json()["message"]

    tool_calls = message.get("tool_calls")
    if not tool_calls:
        return message["content"]

    messages.append(message)
    for call in tool_calls:
        name = call["function"]["name"]
        args = call["function"]["arguments"]
        result = AVAILABLE_FUNCTIONS[name](**args)
        messages.append({"role": "tool", "tool_name": name, "content": str(result)})

    resp = requests.post(
        "http://localhost:11434/api/chat",
        json={"model": model, "messages": messages, "tools": TOOLS, "stream": False},
        timeout=30,
    )
    resp.raise_for_status()
    return resp.json()["message"]["content"]

I ran this exact loop against a mock server shaped like the real Ollama response before trusting the parsing logic: first call returns a tool_calls entry for get_weather, second call (after the tool result goes back in as a role: "tool" message) returns the final answer in plain content. No surprises, no framework, nothing hidden from you when it breaks.

Multi-step tool use is the same loop, just with the if not tool_calls check as your exit condition instead of a single pass. Guard that loop with a max-iteration count the way you would any other agent retry logic, because a model that's confused about whether it already has an answer will happily call the same tool five times in a row.

The Gotcha That Cost Me a Saturday: num_ctx and the OpenAI-Compatible Endpoint

Here's the confusing part. Ollama exposes two ways to talk to it: the native /api/chat endpoint above, and an OpenAI-compatible /v1/chat/completions endpoint for dropping Ollama into tools that already speak the OpenAI SDK. A lot of agent frameworks default to the compatible endpoint because it's the path of least resistance.

The OpenAI-compatible endpoint only maps a fixed allowlist of sampling parameters onto Ollama's internal options. num_ctx, the context window size, isn't on that list.

No error, no warning.

Set it anywhere in the request, nested under options or at the top level, and it's silently dropped. The server just falls back to its own default context length and keeps going.

Why that bit me specifically: your tool schemas and system prompt sit at the front of the context, ahead of the conversation. When the actual window is smaller than you assumed, the front of the prompt is what gets truncated first. It's the same root problem as tool definitions quietly eating a chunk of your context window, just with a worse symptom here: the tools vanish before the model ever reads them, and from the outside it just looks like a model that forgot it has tools, which is exactly the "got dumber overnight" feeling I opened with.

Three ways to actually fix it: set the OLLAMA_CONTEXT_LENGTH environment variable before starting the server, switch to the native /api/chat endpoint and pass options.num_ctx directly (that one's honored), or bake the window into a Modelfile so it travels with the model. I went with the second option, mostly out of spite.

Streaming + Tools: What v0.40.0 Actually Changed

You'll still find tutorials insisting you need stream: false the moment tools enter the picture. That was true. It hasn't been true since mid-2025, when Ollama's streaming tool-calling update shipped, and it got noticeably better again with version 0.40.0, which happened to release the day before I'm writing this.

The old streaming approach waited for the full JSON blob of a tool call before trying to parse it, which worked but occasionally emitted the same tool call twice if a chunk arrived at an awkward boundary. 0.40.0 swaps that for an incremental parser that understands each model's own tool-call template as tokens arrive, instead of treating the whole thing as one opaque string to assemble and parse at the end. Fewer duplicate calls, and streaming plus tools is now just... normal, not a special case you work around.

One more thing that release adds: explicit CAPABILITY declarations in Modelfiles, so a model creator can mark exactly what a model supports. Worth knowing if you're routing requests based on capability: Ollama's new "decision models" (exposed under /v1/systemone) report only a decision capability, specifically so clients don't try to hand them tools. If your router logic assumes every chat model can call tools, that assumption breaks the day you add one of these.

Which Models Actually Call Tools Reliably

Not every model that technically accepts a tools array uses it well. I've burned enough time on this to have opinions, and the pattern has been consistent across everything I've tried.

The malformed-JSON failure mode isn't hypothetical. There's an open GitHub issue with the exact error error parsing tool call: invalid character ']' after object key:value pair. The model itself emitted broken JSON in its tool-call arguments, and Ollama's parser (reasonably) choked on it. That's not an Ollama bug so much as a reminder that the model is generating that JSON token by token, and smaller or less tool-tuned models drop a bracket under pressure the same way they drop a word in a long sentence. It's the same unreliable-output problem I ran into writing about getting validated JSON out of local LLMs with Instructor, just one layer further down, in the tool-call plumbing instead of your own response schema.

I'd skip anything under 7B for a tool loop with more than one step. It's tempting because it's fast and fits on a laptop GPU with room to spare, but you'll spend more time writing retry-and-repair logic around its malformed calls than you saved by not running a bigger model. Before you commit to a model, check the live tools-filtered model list; it moves fast enough that anything I write here will be a little stale within a couple of months.

Ollama's Native Tool Calling vs. LangChain

I'm not anti-LangChain. I've used it, I've written about where it's the right call against CrewAI and AutoGPT-style loops, and it does real work for you once a pipeline gets complex. But "I want my local model to call a Python function" doesn't need a framework, and pretending it does just adds a dependency between you and the actual API response.

Pros of going direct with Ollama's API

  • You see the exact request and response, so a malformed tool call is a JSON blob you can read, not an exception three abstraction layers deep
  • No version-pinning two libraries against each other; it's requests and a dict
  • Streaming, tool calls, and the native options.num_ctx fix all behave exactly as documented, because nothing is translating them first

Cons of going direct with Ollama's API

  • You write your own loop, retry logic, and message-history management, every time
  • No built-in output parsers, no agent memory abstractions, no ecosystem of pre-built tools to import
  • Swapping providers later (say, adding a cloud model as a fallback) means rewriting your request shape instead of swapping a LangChain chat model object

My honest take: for a single-agent loop against one local model, skip the framework. You'll understand your own failures faster. The moment you need multiple agents coordinating, long-term memory, or a provider-agnostic abstraction because you're mixing local and cloud models, that's when the LangChain tax starts paying for itself.

Common Pitfalls

  • Treating arguments as a JSON string. It's already a parsed dict in Ollama's response. Running json.loads() on it raises a TypeError, not a helpful one.
  • Setting num_ctx through the OpenAI-compatible endpoint and assuming it took effect. It's silently dropped. Use the native endpoint or OLLAMA_CONTEXT_LENGTH if context size actually matters, which for tool calling it always does.
  • No cap on the tool-calling loop. A confused model will call the same tool repeatedly instead of answering, the same failure mode I've chased down while debugging infinite loops in CrewAI and LangGraph. Put a hard iteration limit on it from day one.
  • Assuming every chat-capable model calls tools well. Sub-7B models accept the tools field without complaint and still produce malformed calls past the first trivial one.
  • Routing a decision model into your agent loop. Ollama's newer decision models report only a decision capability on purpose: they're not meant to receive tool definitions at all.

Conclusion

If you're building a single local agent against Ollama, start with the raw /api/chat loop above before you reach for a framework. Pin the context length explicitly through the native endpoint, cap your loop iterations, and pick at least an 8B-class model if your tool chain runs more than one step. That's most of what I wish someone had told me before the Saturday I lost to a silently truncated context window. Bring in LangChain later, deliberately, when you actually need the coordination it gives you — not because tool calling on its own seemed like it needed one.

FAQ

Does Ollama support tool calling without LangChain?

Yes. Ollama's native /api/chat endpoint has supported OpenAI-shaped function calling since mid-2024. You send a tools array and read message.tool_calls back, with no framework required. It's a plain HTTP request.

Why are my tool-call arguments not valid JSON when I try to parse them?

Because they're not a string to begin with. Ollama returns arguments as an already-parsed dict, unlike the raw OpenAI API. Skip the json.loads() call entirely and use the dict directly.

Which Ollama models are best for tool calling?

Anything under 7B parameters is unreliable past a single trivial tool call. Mid-to-large tool-tuned models like Qwen3, Llama 3.3, and Mistral Small 3.5 call tools correctly and know when to stop. See Ollama's tool-calling reference for the full request and response shape, and check the live model list before committing, since new models ship constantly.

Why did my agent stop using its tools with no error?

Most likely a context-window problem. If you're calling Ollama through its OpenAI-compatible endpoint, num_ctx isn't on the mapped parameter list and gets silently dropped, which means your tool schemas can get truncated out of the context before the model reads them. Switch to the native /api/chat endpoint and pass options.num_ctx directly, or set OLLAMA_CONTEXT_LENGTH on the server.

Do I need streaming disabled to use tool calling with Ollama?

No, not anymore. That was a real limitation before mid-2025. Ollama's streaming tool-calling update fixed it, and version 0.40.0 improved it further with an incremental parser that reduces duplicate tool calls during streaming.
