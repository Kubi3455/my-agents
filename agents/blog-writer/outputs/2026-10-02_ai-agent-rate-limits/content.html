Three weeks ago I kicked off an overnight CrewAI run against a model API with a generous-sounding “enterprise” quota. Forty research agents, fanning out in parallel, each one calling the model half a dozen times to plan, search, and summarize. I woke up to a wall of red: HTTP 429, AI agent rate limits blowing past every retry, for six straight hours, with the job maybe a third done.

If you've scaled a single-agent prototype into anything with more than one worker hitting the same model, you already know this feeling. It's the same sinking one I had the weekend I spent chasing infinite loops in CrewAI and LangGraph, except this time the agents weren't stuck. They were just all talking to the model at once, slamming straight into AI agent rate limits, and the error messages rarely tell you what actually went wrong.

Here's what actually causes AI agent rate limits to blow up a pipeline, how to tell a 429 you should retry from one you shouldn't, and the backoff, concurrency, and idempotency code that stopped mine from DDoS-ing itself the second time around.

Why AI Agent Rate Limits Hit Harder Than a Single API Call

A chatbot makes one model call per user turn. An agent pipeline makes a dozen. Plan the task, call a tool, read the result, decide whether to call another tool, summarize, maybe hand off to a second agent that repeats the whole thing. Multiply that by however many agents you're running concurrently and the request count stops looking like your traffic and starts looking like a load test against someone else's API.

The math gets ugly fast. Fan out to roughly twenty model calls per task, and twenty-five concurrent tasks can saturate a 500-requests-per-minute quota before a single retry even fires. I'd read that number before I built my own pipeline and thought it sounded pessimistic. It isn't. I counted mine afterward: twenty-three calls per task, mostly tool-use round trips I hadn't accounted for.

Some of that overhead isn't even your prompt. If you've got a handful of MCP servers wired into the same agent, the tool definitions alone can eat a third of your context window before the model reads your actual request, which means more input tokens per call, which eats into the token-per-minute side of the same rate limit. Burning your budget on definitions you don't use in that turn is its own kind of self-inflicted 429.

My instinct, given that history, was to blame the agent logic again. It wasn't the logic. It was volume, and volume needs a different fix than a broken exit condition does.

What a 429 Actually Tells You (Read the Body, Not Just the Status Code)

Here's the confusing part: not every 429 means the same thing, and treating them all as "wait and retry" is how people burn through their retry budget on an error that will never succeed no matter how long they wait.

Anthropic's API returns a 429 for an ordinary rate limit, with a retry-after header telling you how many seconds to wait. But it also returns a 429 when you've crossed your organization's monthly spend cap, and that response has no retry-after header at all, because waiting won't help. The body looks like this:

{
  "type": "error",
  "error": {
    "type": "rate_limit_error",
    "message": "You have reached your API usage limits: your organization has crossed its monthly API usage threshold...",
    "details": { "error_code": "enforced_spend_limit_reached" }
  },
  "request_id": "req_018EeWyXxfu5pfWkrYcMdjWG"
}

Same error.type as a normal rate limit. The only thing that tells you it's hopeless is error.details.error_code. Retry that one on a loop and you'll just burn through your attempt budget waiting for a reset that was never coming this month.

OpenAI's error code reference splits it differently. A genuine rate limit comes back as a 429 with type: "rate_limit_error" and code: "slow_down", and the docs note this can fire "even when your traffic is within its requests-per-minute and tokens-per-minute limits," because short bursts get smoothed, not measured at face value. Model overload is a separate case entirely: a 503 with type: "service_unavailable_error" and code: "server_is_overloaded". That one is also worth retrying, just on a longer, lazier backoff, since it's a capacity problem on their end, not a limit on yours.

The practical rule I use now: check the error code before you decide to retry, not just the status code. A 429 is not a monolith.

Backoff With Jitter, Done Right

You'll see people recommend a flat "sleep 5 seconds and try again." It works, until five agents hit the same limit at the same moment, sleep the same five seconds, and slam the API again in perfect unison. That's a thundering herd, and it's self-inflicted.

I use tenacity for this instead of hand-rolling it, mostly because I trust a library that's been through more edge cases than my Tuesday-afternoon implementation has. The part that actually matters is telling it which exceptions deserve a retry and which don't:

from tenacity import (
    retry, retry_if_exception_type, stop_after_attempt, wait_random_exponential
)

class RateLimitError(Exception):
    """Transient: requests-per-minute or tokens-per-minute cap."""

class QuotaExceededError(Exception):
    """Permanent for now: spend cap or monthly quota. Don't retry."""

@retry(
    wait=wait_random_exponential(multiplier=1, max=30),
    stop=stop_after_attempt(5),
    retry=retry_if_exception_type(RateLimitError),
    reraise=True,
)
def call_model(prompt: str) -> str:
    response = client.send(prompt)
    if response.status_code == 429:
        code = response.json()["error"].get("details", {}).get("error_code", "")
        if code == "enforced_spend_limit_reached":
            raise QuotaExceededError(response.text)
        raise RateLimitError(response.text)
    return response.json()["content"]

wait_random_exponential is the jitter part: each retry waits roughly double the last one, plus a random amount, so five agents that failed together don't retry together. retry_if_exception_type(RateLimitError) is the part that stops a quota error from eating five attempts for nothing; QuotaExceededError just isn't in that set, so it reraises on attempt one. I ran this against a mock client that fails twice then succeeds, and separately against one that always raises QuotaExceededError, before trusting it on a real pipeline. The second case should fail immediately, not after five sleeps.

I'd already written almost this exact pattern once before, for the retry and exit strategies that keep an agent from looping forever on a bad tool call. Rate-limit backoff and loop-exit logic turn out to share a parent: both need a hard stop_after_attempt, or "retry until it works" quietly becomes "retry forever."

Cap Concurrency Before You Even Hit the Wall

Backoff fixes a 429 after it happens. The annoying part? By the time you're backing off, you've already wasted a request and however many seconds the retry costs. Capping how many agents can call the model at once is cheaper, because it prevents the error instead of recovering from it.

Anthropic's rate limiter uses a token bucket: capacity refills continuously instead of resetting on a fixed clock tick. A simple client-side token bucket that mirrors the same idea keeps your fan-out under the ceiling without you having to guess at sleep durations:

import threading
import time

class TokenBucket:
    def __init__(self, rate_per_minute: int, capacity: int):
        self.rate_per_second = rate_per_minute / 60.0
        self.capacity = capacity
        self.tokens = float(capacity)
        self.last_refill = time.monotonic()
        self.lock = threading.Lock()

    def acquire(self, cost: float = 1.0) -> None:
        while True:
            with self.lock:
                now = time.monotonic()
                elapsed = now - self.last_refill
                self.last_refill = now
                self.tokens = min(self.capacity, self.tokens + elapsed * self.rate_per_second)
                if self.tokens >= cost:
                    self.tokens -= cost
                    return
            time.sleep(0.01)

# 480 RPM budget, shared by every agent worker thread
request_budget = TokenBucket(rate_per_minute=480, capacity=20)

def call_with_budget(prompt: str) -> str:
    request_budget.acquire()
    return call_model(prompt)

Every worker calls acquire() before it touches the model, full stop. No budget left, no call, the thread just waits its turn instead of firing off a request that was going to 429 anyway. I'd set the capacity low on purpose, well under the organization's actual limit, because other things share that quota too: your eval runs, a teammate's script, whatever's hitting the same API key.

One honest caveat: this only helps if your pipeline is actually hitting a shared cloud API. If you're running models locally through Ollama, none of this applies until you hit your own GPU's throughput, which is a real ceiling too, just a different one with no 429 to warn you about it.

Make Retries Idempotent (Or Your Retry Will Double-Charge Someone)

Here's the thing nobody mentions in the backoff tutorials: retrying a model call is safe. Retrying a tool call the model made often isn't. If an agent calls a "charge the customer" or "send the email" tool, gets a 429 on the response that would have confirmed success, and retries the whole step, you can end up running that tool twice for one logical action.

The fix is a fingerprint, not a retry count. Before a tool with a side effect runs, hash the agent, the tool name, and the arguments, and check whether you've already run that exact call:

import hashlib

_seen_calls: dict[str, object] = {}

def fingerprint(agent_id: str, tool_name: str, args: dict) -> str:
    payload = f"{agent_id}:{tool_name}:{sorted(args.items())}"
    return hashlib.sha256(payload.encode()).hexdigest()

def run_tool_once(agent_id: str, tool_name: str, args: dict, fn):
    key = fingerprint(agent_id, tool_name, args)
    if key in _seen_calls:
        return _seen_calls[key]
    result = fn()
    _seen_calls[key] = result
    return result

I tested this against a fake "charge the card" function that increments a counter: two calls with identical arguments, one actual charge. That's the whole point, a replayed retry returns the cached result instead of running the side effect again. For anything that matters, swap the in-memory dict for a real cache with a TTL. A dict that lives for the length of one process won't save you across a restart.

This is also where I'd pull in a person rather than trust the retry logic blindly. For a tool that moves money or sends something irreversible, keeping a human in the loop on the first few runs catches the fingerprint bugs you didn't think to write a test for, before they cost anything real.

Pros and Cons of Letting the SDK Auto-Retry

Both the Anthropic and OpenAI SDKs retry certain errors for you automatically, with no code on your end. Tempting to just rely on that and skip everything above. I'd only do it for small, low-concurrency scripts.

Pros of SDK auto-retry

  • Zero code, zero maintenance for the common case
  • Already tuned against the provider's own rate limit behavior
  • Honors retry-after correctly out of the box

Cons of SDK auto-retry

  • No visibility into how many retries happened unless you add logging yourself
  • Doesn't know about your tool-call side effects, so it can't help with idempotency
  • Doesn't coordinate across workers, so twenty agents can still synchronize a thundering herd even if each one's retries look fine in isolation
  • Caps out at a fixed attempt count the SDK chose, not one you tuned for your traffic pattern

For anything with more than a handful of concurrent workers, I'd layer the token bucket and fingerprinting on top of the SDK's built-in retry rather than replacing it. Skip rebuilding exponential backoff from scratch; that part the SDK already does fine.

Common Pitfalls

  • No stop_after_attempt. "Retry until it works" on a quota error becomes an infinite loop that never exits.
  • Retrying a spend-cap or quota error at all. Check error_code/code first; some 429s have no fix but waiting for next month.
  • Flat sleep durations with no jitter. Every failed worker wakes up at the same instant and re-triggers the exact storm you were recovering from.
  • Treating a 503 overload the same as a 429 rate limit. Both deserve a retry, but overload is a capacity problem on their side and tolerates a longer, lazier backoff.
  • Retrying side-effecting tool calls without a fingerprint. Fine for a read-only search tool. At scale, with a payment or email tool, that's how a $1 charge becomes $2.

Conclusion

If you only do one thing from this post, make it the error-code check before the retry decision. It's a five-line change and it's the difference between a pipeline that recovers gracefully and one that burns its whole attempt budget on an error that was never going away. After that, add the token bucket; it's less code than the backoff logic and it prevents more errors than the backoff ever recovers from. Idempotency can wait until you actually have a tool with a side effect worth protecting, but don't wait until after the double-charge to write it.

FAQ

What's the difference between a rate limit 429 and a quota or spend-cap 429?

Both return the same HTTP status and often the same error type, but a rate limit is temporary and includes a retry-after header telling you when it clears. A spend-cap or quota error has no such header, because nothing you do will fix it before the billing period resets. Check the error code, not just the status.

Should I add jitter if I only run one agent at a time?

Less urgent, but still worth it. Jitter mostly protects you from synchronizing with other workers, including other processes on your own machine or a teammate's script hitting the same API key. A single lonely agent gains less from it, though exponential backoff alone is still better than a flat sleep.

How many retries should stop_after_attempt allow?

I use 5 as a default and haven't needed more in practice. If you're hitting the cap at 5 attempts regularly, the real fix is the token bucket from earlier, not a higher retry count. A higher number just delays the failure instead of preventing it.

Does prompt caching actually help with rate limits, or just cost?

Both, on Anthropic's API specifically: cached input tokens don't count toward your input-tokens-per-minute limit on most models, so a high cache hit rate raises your effective throughput, not just your bill. It won't touch your requests-per-minute limit, though, so it's a partial fix at best for an agent pipeline making many small calls.
