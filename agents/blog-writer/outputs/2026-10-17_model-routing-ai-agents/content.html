Last Tuesday, mid-batch, every call to our primary provider started timing out. Not slow. Timing out, hard, after thirty seconds, over and over, for forty minutes straight. The agents didn't crash. They just sat there, retrying a dead endpoint, burning through real customer tickets while doing nothing useful.

If you've run an agent against one provider in production, you know this feeling. Your code is fine. The thing that's down isn't, and your retry loop just keeps hammering it anyway.

So here's what I actually changed, and what I learned building model routing for AI agents the hard way: where a hand-rolled circuit breaker is enough, where LiteLLM's Router or OpenRouter's `models` parameter save you real work, and the one mistake that will make your fallback invisible until it's already cost you money.

Why model routing for AI agents matters more in 2026

A year or two ago, most agent projects were calling one provider and treating an API error as an edge case worth a try/except and a log line. That stopped being good enough once agents moved from a demo running for five minutes to a worker running for eight hours. Over a long enough run, "the provider had a bad ten minutes" isn't an edge case. It's Tuesday.

Model routing for AI agents, in the sense this article uses it, is specifically about what happens when your current model or provider stops answering: you need a backup model, a way to detect the failure fast, and a way to switch without the rest of your pipeline noticing. That's a different problem from rate limiting, and it's worth being precise about the difference, because the fix for one makes the other worse if you mix them up.

I'd also point out this isn't the same problem as surviving a process crash. If your worker dies mid-task, that's a job for durable workflow recovery, replaying from a checkpoint. Model routing assumes your process is alive and healthy. The thing that's broken is the thing on the other end of the HTTP call.

What actually breaks when a provider goes down

"The provider is down" covers at least four different failure shapes, and each one wants a different response:

  • Hard failure — connection refused or a 5xx, usually fast. Switch immediately.
  • Slow failure — the connection stays open and just doesn't respond. This is the dangerous one, because without a tight timeout your agent looks "fine" while doing nothing.
  • Rate limiting: a 429 on an otherwise healthy provider. Covered in depth in our practical retry strategy for 429 errors; the short version is you retry the same provider with backoff, you don't route away from it.
  • Silent degradation: the provider answers, but slower, or with a model that's been quietly swapped to a cheaper variant under load. Nothing errors. Your p99 latency just creeps up.

Here's the part that trips people up: a retry loop tuned for rate limits is close to the worst possible response to a hard failure. Backing off and retrying the same dead endpoint for sixty seconds, three times, before giving up is exactly what burned forty minutes of my overnight batch. The fix for "provider down" is routing away, fast. The fix for "provider rate-limited" is waiting and retrying the same provider. Treating them as one problem is how you get my Tuesday.

The DIY option: a circuit breaker in front of your LLM calls

Before reaching for a proxy or a routing API, it's worth understanding the pattern underneath both of them, because you'll need it even when a library is doing the work for you. A circuit breaker wraps a risky call and tracks failures. Trip enough of them in a row, and the breaker "opens": it stops calling the real function entirely and fails fast instead, for a cooldown window, before cautiously letting one call through to test the water again.

pybreaker is a small, well-established implementation of exactly this. I installed it and ran this directly rather than trust a blog post's description of the behavior:

import pybreaker

class FakeProviderDown(Exception):
    pass

breaker = pybreaker.CircuitBreaker(fail_max=3, reset_timeout=5)

def call_primary():
    raise FakeProviderDown("503 from primary provider")

for i in range(5):
    try:
        breaker.call(call_primary)
    except pybreaker.CircuitBreakerError as e:
        print(i, "CIRCUIT OPEN ->", str(e)[:80])
    except FakeProviderDown as e:
        print(i, "real failure ->", e, "| state:", breaker.current_state)

The actual output:

0 real failure -> 503 from primary provider | state: closed
1 real failure -> 503 from primary provider | state: closed
2 CIRCUIT OPEN -> Failures threshold reached, circuit breaker opened
3 CIRCUIT OPEN -> Timeout not elapsed yet, circuit breaker still open
4 CIRCUIT OPEN -> Timeout not elapsed yet, circuit breaker still open

Where this breaks: the exception you catch changes

Look closely at that output again. Calls 0 and 1 raise FakeProviderDown, your real exception. Call 2 trips the breaker and raises pybreaker.CircuitBreakerError instead. Calls 3 and 4 never touch call_primary() at all. If your error-handling code only catches the original exception type (which is the natural thing to write first), it will work fine in testing and then silently stop catching anything the moment the breaker opens in production. I'd wrap the breaker's own error type in the same except block from day one, not after the first on-call page.

pybreaker's real constructor defaults to fail_max=5, reset_timeout=60, with a success_threshold for how many clean calls it needs before fully closing again. For a single LLM call this is a solid starting point. By itself it isn't model routing. It tells you when to stop calling a broken thing, but you still have to write the part that calls something else instead. That's where the next two options come in.

LiteLLM Router: fallbacks as config, not application code

LiteLLM's proxy treats fallback as a first-class, declarative concept instead of something you hand-roll per call site. You list backup model groups, and the proxy tries them in order when the primary fails:

# litellm proxy config.yaml (verified field names against the official docs)
litellm_settings:
  num_retries: 3          # retry the same model this many times first
  request_timeout: 10     # seconds, before counting as a failure
  default_fallbacks: ["claude-opus"]   # catch-all for any unmapped model

router_settings:
  fallbacks: [{"gpt-5-main": ["gpt-5-backup", "claude-sonnet"]}]
  context_window_fallbacks: [{"gpt-5-main": ["claude-opus"]}]
  content_policy_fallbacks: [{"gpt-5-main": ["claude-sonnet"]}]
  allowed_fails: 3     # cooldown threshold per deployment
  cooldown_time: 30    # seconds a failing deployment is skipped

Three separate fallback lists matter here, and conflating them is an easy mistake: plain fallbacks handles ordinary errors like rate limits and downtime, context_window_fallbacks only fires when the input is too long for the current model, and content_policy_fallbacks only fires on a moderation rejection. Routing a context-length failure through your downtime fallback chain just wastes a call on a model that will reject the same oversized input for the same reason.

The allowed_fails / cooldown_time pair is the proxy's built-in circuit breaker: once a deployment crosses the failure threshold, it's skipped for the cooldown window across every request, not just the one that triggered it. That's a meaningfully different behavior from the pybreaker example above, where the breaker only protects the one call site it wraps. You also get a disable_fallbacks flag you can set per request or per API key, which matters more than it sounds like once you've got a background job that should fail loudly instead of quietly degrading to a weaker model.

Pros of LiteLLM Router

  • One config file covers every call site; you don't scatter fallback logic across your codebase
  • Three distinct fallback types (downtime, context window, content policy) instead of one bucket
  • Cooldown is shared across all requests through the proxy, not per call site
  • Spend logs record attempted_fallbacks and original_model_group, so you can actually see how often fallback fired

Cons of LiteLLM Router

  • You're running (and operating) a proxy process, which is one more thing to keep alive
  • Config lives outside your application code, which is easy to forget about during an incident unless it's in version control somewhere obvious
  • As of Proxy v1.85.0, the mock_testing_fallbacks flags that make it easy to force-test a fallback path in a dev environment were removed from the Proxy itself; they still work if you're calling litellm.Router directly in Python instead

OpenRouter: routing at the API layer

If you don't want to run a proxy, OpenRouter pushes the same idea into the request body itself. The main mechanism is a models array, a priority-ordered list OpenRouter walks through when the primary model's provider is down:

from openai import OpenAI

client = OpenAI(
    base_url="https://openrouter.ai/api/v1",
    api_key="sk-or-...",
)

response = client.chat.completions.create(
    model="openai/gpt-5-main",
    messages=[{"role": "user", "content": "Summarize this ticket."}],
    extra_body={"models": ["openai/gpt-5-main", "anthropic/claude-sonnet-5"]},
)
print(response.model)  # whichever model actually answered

Billing is based on whichever model ends up in response.model, which is the one thing I'd actually check in your logs after switching this on; I've seen people assume the first entry in the list is what they paid for and never notice when the second one quietly took over for a week.

If you're calling OpenRouter through its Anthropic-shaped endpoint specifically, there's a second, stricter parameter called fallbacks instead of models. It caps out at exactly 3 entries, each entry accepts nothing but a model field (trying to override max_tokens or similar per fallback attempt gets you a 400), and sending both models and fallbacks on the same request is also a 400. Worth knowing before you copy a models array example into Anthropic-endpoint code and wonder why it's rejected.

Pros of OpenRouter

  • No proxy to run; fallback is a field on the request you're already making
  • Triggers on a wide default set: context length errors, moderation flags, rate limits, downtime
  • Access to models from multiple labs through one API key and billing relationship

Cons of OpenRouter

  • You're routing through a third party between you and the model provider, which is its own dependency to go down
  • The stricter fallbacks parameter (3 entries, model-only) only applies on the Anthropic-shaped endpoint, which is an easy detail to miss if you're used to the plain models array
  • No cooldown/circuit-breaker concept of its own; it retries the fallback list per request, so a provider that's fully down still gets hit on every single call until it recovers

Circuit breaker vs. LiteLLM Router vs. OpenRouter

The trap nobody mentions: a silent fallback changes your agent's behavior

Here's the thing that actually worries me about all three options above: every one of them is designed to make the switch invisible. That's the point, and it's also the trap. The moment your agent falls back from a frontier model to a smaller or different one, you've changed the thing actually making decisions, and nothing in your pipeline necessarily tells you that happened.

Two specific ways this bites you. First, structured output and tool-calling behavior aren't identical across providers, even when the API shape looks similar on paper. A tool schema that Claude handles one way and a GPT model handles slightly differently can produce a response that parses fine but means something subtly different; this is the same class of problem covered in our look at Claude Agent SDK vs. OpenAI Agents SDK, and it gets worse, not better, when the switch between them happens automatically mid-run instead of at deploy time. Second, if your agent makes parallel tool calls, a fallback model that handles concurrency differently can change the order or grouping of those calls in ways your downstream code wasn't written to expect.

The only real fix is visibility, not prevention. You can't stop providers from going down. You can make sure you'd notice when your agent quietly started running on a different model for an hour. That means tracing which model actually answered each call, not just whether the call succeeded, and alerting on a sustained shift, not a single fallback event.

Common pitfalls

  • Routing rate limits like outages. A 429 on a healthy provider wants backoff-and-retry on the same provider, not a switch. Mixing the two policies is how a brief rate limit turns into an unnecessary model swap, or a real outage turns into forty minutes of useless retries.
  • Catching only the original exception type. Once a circuit breaker opens, you get its error, not the provider's. Test the open-circuit path specifically, not just the first failure.
  • Stacking too many fallbacks. Each hop adds its own timeout before failing over. A three-model chain with a 10-second timeout per hop can mean a 30-second wait before anything useful happens. Keep the chain short, or lower the per-hop timeout as you go deeper into it.
  • No cost or quality floor. If your fallback chain can land on a much cheaper or weaker model with no limit, a long outage can quietly shift your entire workload onto a model that was never meant to carry it, with a bill and an error rate to match.
  • Forgetting the Anthropic-endpoint limits on OpenRouter. The fallbacks parameter there caps at 3 entries and rejects per-attempt overrides; code copied from a models-array example will 400.

Conclusion

If you're running a single agent against a single provider in anything other than a weekend project, I'd start with a circuit breaker around the call, today, before you need it. It's the smallest piece, and it teaches you the failure modes you'll need to reason about no matter which routing layer you add later. Once you've got more than one service calling more than one model, move that policy into LiteLLM's Router so it isn't duplicated and drifting across your codebase. Reach for OpenRouter when you'd rather not run a proxy at all and you're fine with its cooldown being per-request instead of shared.

Whatever you pick, wire in the tracing before the outage, not during it. The failure you can't see is the one that costs you the most.

FAQ

Is model routing the same thing as retrying on a rate limit?

No. Rate-limit retries wait and try the same provider again, which we cover separately in our 429 retry strategy guide. Model routing switches to a different model or provider because the original one is down, not just busy.

Do I need LiteLLM or OpenRouter if I only call one provider?

Not necessarily. A circuit breaker plus a single manually chosen backup model is often enough until you're running several services against several providers at once. Add a routing layer when the policy itself starts getting duplicated.

Will a fallback model break my structured outputs or tool calls?

It can. Different providers don't handle tool schemas and structured output identically, so a fallback can produce a response that parses correctly but means something subtly different. Trace which model actually answered, not just whether the call succeeded.

How many fallback models should be in my chain?

Keep it short. Each hop adds its own timeout before giving up, so a long chain can mean a long wait before anything useful happens. Two or three well-chosen backups beat a long list of untested ones.

What's the actual difference between LiteLLM's three fallback types?

fallbacks handles ordinary errors like downtime and rate limits, context_window_fallbacks only fires when the input is too long for the current model, and content_policy_fallbacks only fires on a moderation rejection. Routing the wrong failure through the wrong list wastes a call on a model that will fail for the same reason.
