Last month I shipped a support agent that looked flawless in every demo I ran. Ask it to refund an order and it called the right tool, then replied with a clean confirmation. Three days later, a customer asked why they'd been refunded twice for $42. The agent's final message both times had said exactly the right thing: "Refunded $42.00 for order 4821." Nothing in the output was wrong. The path it took to get there was.

If you've shipped multi-step tool calls before, you know how this goes. Most teams' process for evaluating AI agents before production stops at a green eval dashboard and a demo recording that looks great. Then something neither of those tested for shows up in production, usually discovered by a support ticket instead of a test. The final answer being correct tells you almost nothing about whether the steps that produced it were safe, efficient, or even sane.

Here's what actually catches this before your users do: grading the path your agent took, not just where it landed. I'll walk through evaluating AI agents before production with real trajectory-matching code, show you a match mode that quietly fails to catch the exact bug it exists to catch, and get into when an LLM-as-judge setup is worth the extra cost over a plain output check.

Evaluating AI agents before production: why "it worked in the demo" is a trap

Agents are statistically unreliable across repeated attempts, even with an unchanged prompt and an unchanged input. Run the same refund request ten times and you might get the same clean path nine times and a double tool call once, because the model occasionally decides to "double-check" after a slow tool response. A single passing run tells you that path exists. That's all it tells you.

It doesn't matter much which control flow your agent runs on, either. A tight ReAct loop and a plan-and-execute setup fail in different shapes, but they both produce a trajectory you haven't looked at yet.

This is the part that's easy to skip when you're under deadline pressure: a demo is one sample. Production is thousands of samples a day, and the rare path shows up eventually. The fix isn't "test more demos." It's testing the actual sequence of decisions, not just the sentence at the end of it.

Outcome grading vs. transcript grading, and why you need both

Anthropic's own engineering guide on agent evals draws a sharper line here than most third-party blog posts do, and it's worth reading straight instead of through a summary. The outcome is the environment's final state, not what the agent claims happened; for a booking agent, the outcome is whether the reservation actually exists in the database, not the confirmation text. Anthropic's guidance is that it's "often better to grade what the agent produced, not the path it took," because deterministic outcome checks are cheap, don't depend on a second LLM's judgment, and are hard to game.

So why bother with trajectories at all? Because an outcome check alone would have told me my refund agent was working. The order got refunded, the database state was right from the final transaction's point of view. Outcome grading didn't have a slot for "and also, don't do that twice." That's exactly the gap transcript grading fills: once you have outcome tests in place, Anthropic recommends also grading the transcript for things like tool-use behavior, unnecessary steps, or an unsafe call that happened to get overwritten by a later correct one. Transcript and outcome aren't competing approaches. Outcome is your primary signal; transcript is how you catch the stuff outcome checks structurally can't see.

What's actually inside a trajectory

A transcript (also called a trace or trajectory) is, in Anthropic's own words, "the complete record of a trial, including outputs, tool calls, reasoning, intermediate results, and any other interactions." For an API-based agent, that's the full messages array an eval run produces: the user turn, every assistant message (including ones that are nothing but a tool call), every tool result, and the final reply.

That messages array is also the thing you already have if you've set up any kind of tracing for your agent. Tracing and trajectory evals aren't separate infrastructure projects; the trace is the data, and the evaluator is the grading logic you run against it, either in CI before a release or against sampled production traffic after one. Worth a check here, too: if you haven't dealt with context bloat yet, every intermediate tool result in that array is now also something your evaluator has to read.

Build your test set from real failures, not synthetic ones

I'd skip the instinct to wait until you have a few hundred test cases before trusting any of this. Anthropic's guidance is blunt about it: "20-50 simple tasks drawn from real failures is a great start." Teams that wait for a big, comprehensive dataset usually ship nothing, because the dataset never feels done. Start smaller than feels responsible, and grow it from whatever breaks.

The annoying part is where those first cases come from: your own manual checks and whatever a user already complained about. Every production failure is a test case you didn't have to invent. My double-refund incident became test case #1 the same afternoon it was reported.

One more detail that's easy to get wrong and expensive when you do: isolate every test run from a clean environment. This gets harder once your agent can survive a restart. If you're using something like Temporal for crash recovery, double-check that a replay doesn't resurrect state left over from a previous, failed attempt. Shared state between trials doesn't just risk a flaky test, it can quietly inflate your scores. Anthropic's post includes a genuinely surprising real example: in one of their own eval runs, Claude got an unfair advantage on a coding task by reading leftover git history from an earlier trial that hadn't been cleaned up. The agent wasn't cheating on purpose. The setup just handed it information it shouldn't have had.

Trajectory matching with AgentEvals

For the mechanical side of trajectory grading, LangChain's open-source agentevals package (pip install agentevals) does the comparison work so you don't hand-roll a diff over tool-call lists. Per the LangSmith trajectory evals docs, create_trajectory_match_evaluator compares your agent's actual messages against a reference trajectory you wrote by hand for that test case:

from agentevals.trajectory.match import create_trajectory_match_evaluator

evaluator = create_trajectory_match_evaluator(trajectory_match_mode="unordered")

outputs = [
    {"role": "user", "content": "Refund order 4821"},
    {"role": "assistant", "content": "", "tool_calls": [
        {"function": {"name": "lookup_order", "arguments": '{"order_id": "4821"}'}}]},
    {"role": "tool", "content": "status: paid, amount: 42.00"},
    {"role": "assistant", "content": "", "tool_calls": [
        {"function": {"name": "issue_refund", "arguments": '{"order_id": "4821", "amount": 42.00}'}}]},
    {"role": "tool", "content": "refund issued"},
    # the bug: the agent calls issue_refund a second time
    {"role": "assistant", "content": "", "tool_calls": [
        {"function": {"name": "issue_refund", "arguments": '{"order_id": "4821", "amount": 42.00}'}}]},
    {"role": "tool", "content": "refund issued"},
    {"role": "assistant", "content": "Refunded $42.00 for order 4821."},
]

reference_outputs = [
    {"role": "user", "content": "Refund order 4821"},
    {"role": "assistant", "content": "", "tool_calls": [
        {"function": {"name": "lookup_order", "arguments": '{"order_id": "4821"}'}}]},
    {"role": "tool", "content": "status: paid, amount: 42.00"},
    {"role": "assistant", "content": "", "tool_calls": [
        {"function": {"name": "issue_refund", "arguments": '{"order_id": "4821", "amount": 42.00}'}}]},
    {"role": "tool", "content": "refund issued"},
    {"role": "assistant", "content": "Refunded $42.00 for order 4821."},
]

result = evaluator(outputs=outputs, reference_outputs=reference_outputs)
print(result)
# {'key': 'trajectory_unordered_match', 'score': False, 'comment': None, 'metadata': None}

Good, that's exactly what I want: score: False, because the actual trajectory has an extra issue_refund call the reference doesn't. unordered mode means it doesn't care that lookup_order and issue_refund happened in a different order than the reference, only that the same set of calls happened. That's the right amount of strictness for a lot of agents, since the model is free to reorder independent steps without that being a real failure.

The catch: the wrong match mode will wave this straight through

Here's the part that isn't in any tutorial I read before building this: agentevals also ships a superset mode, which accepts the actual trajectory as valid if it contains the reference trajectory's calls plus possibly more. Swap trajectory_match_mode="unordered" for trajectory_match_mode="superset" in the exact same test above, and the result flips to {'key': 'trajectory_superset_match', 'score': True, ...}. The duplicate refund passes clean, because "superset" only checks that the reference calls are present, and never flags the extra one.

That shape of bug, two writes landing because of a slow response or a retry, is close cousin to the race conditions that show up when tool calls run in parallel against shared state. Same root cause. Different trigger.

I ran both modes against the same duplicate-call trajectory before I trusted either of them, and I'd recommend you do the same with your own agent before picking a mode. superset reads like the "more forgiving, fewer false alarms" option, and for some workflows it is. For anything where an extra tool call is the actual failure mode you're hunting (a second refund, a second email send, a second database write), it's the one mode that structurally can't catch it. Reach for unordered or strict when duplicate or unsafe calls are the thing you're testing for, not superset.

When there's no single right path: LLM-as-judge

Exact matching works when you can write down one correct sequence of tool calls. A lot of real tasks don't have one. "Research this topic and summarize it" might legitimately call a search tool twice, or once, or three times, depending on what the first result returns. For those, agentevals provides create_trajectory_llm_as_judge, which scores a trajectory against a rubric instead of a fixed reference:

from agentevals.trajectory.llm import create_trajectory_llm_as_judge, TRAJECTORY_ACCURACY_PROMPT

evaluator = create_trajectory_llm_as_judge(
    prompt=TRAJECTORY_ACCURACY_PROMPT,   # default rubric, no reference required
    model="openai:o3-mini",
    feedback_key="trajectory_accuracy",  # the default feedback_key, shown explicitly here
)

result = evaluator(outputs=outputs)
# -> {"key": "trajectory_accuracy", "score": True | False, "comment": "..."}

The built-in rubric grades whether the trajectory "makes logical sense between steps," shows "clear progression," and is "relatively efficient, though it does not need to be perfectly efficient." There's also a reference-aware variant, TRAJECTORY_ACCURACY_PROMPT_WITH_REFERENCE, for when you have an example of a good path but want to allow reasonable variation instead of an exact match.

Honest caveat: the OpenAI account I had available for this piece was out of credit, so I verified the function signature, the default feedback_key, and the exact wording of the built-in rubric by reading the installed package's source directly rather than from a live model call. The code above is accurate to the library as published; I just didn't get to watch o3-mini grade this specific transcript in front of me, and I'm saying so instead of pretending otherwise.

The honest tradeoff with an LLM judge: it costs a model call per evaluation, it can disagree with itself across runs, and it's a second model forming an opinion about a first model's behavior. I'd default to trajectory matching wherever a reference path is reasonable to write down, and only bring in the judge for the genuinely open-ended tasks where it isn't.

The math nobody wants to hear: why 95% per step still isn't enough

If each step in your agent's plan succeeds independently 95% of the time, and the task takes eight steps, the odds every single step lands correctly aren't 95%. They're 0.95 raised to the eighth power:

>>> 0.95 ** 8
0.6633956609125211

Sixty-six percent. A per-step success rate that sounds production-ready turns into a one-in-three failure rate the moment you chain eight of them together. And that's the optimistic version of the math, because it assumes each step's success is independent of the ones before it, which it isn't. A wrong result at step two gets fed into step three as if it were correct. Real compounding is usually worse than the clean exponent suggests, not better.

This is exactly why checking "did the eval pass once" isn't the same question as "will this hold up over a thousand runs." It's also why pass rate alone, measured once, is the wrong metric for anything multi-step. Anthropic's eval guide distinguishes two ways of running the same task multiple times: pass@k, the odds of at least one success in k attempts, which climbs toward 100% as k grows and suits a one-shot coding tool where you just need one good answer; and pass^k, the odds that all k attempts succeed, which falls toward 0% as k grows and is the number that actually matters for a customer-facing agent that needs to be consistently right, not occasionally right.

Picking the right grading approach

If your stack is already OpenAI-centric, their trace grading workflow covers similar ground from a dashboard instead of code: open a trace under Logs > Traces, create a grader against it, then use "Grade all" to run that grader across many examples at once. It's a reasonable option if you'd rather click through a UI than write Python, though you give up the version-controlled, CI-friendly reference trajectories that agentevals gives you.

Pros of trajectory-level testing

  • Catches a correct-output-but-wrong-path bug that outcome checks structurally can't see
  • Exact trajectory match is deterministic and cheap to run in CI, no extra model call
  • Turns one production incident into a permanent regression test in minutes

Cons of trajectory-level testing

  • Writing a reference trajectory for every test case is real, ongoing work
  • Exact match modes are brittle against legitimate path variation
  • The wrong match mode (like superset) can silently stop catching the bug you built the test for

Common pitfalls

  • Picking a lenient match mode by default. superset feels safer because it has fewer false alarms, but it's the one mode that won't flag an unsafe extra call. Match the mode to the failure you're actually worried about.
  • Waiting for a big dataset before testing anything. 20-50 cases from real failures beats zero cases while you wait to feel ready.
  • Letting state leak between test runs. A leftover file, a warm cache, or old history from a previous trial can hand the agent information it wouldn't have in a clean run, and quietly inflate your scores.
  • Reporting a single pass rate for a multi-step agent. Decide whether you care about pass@k or pass^k before you pick the number you report, they measure different things and can both be true of the same agent.

Conclusion

If you only have time for one change this week, it's this: take whatever incident you're still a little embarrassed about, and turn it into a trajectory test case before you fix the underlying bug. You'll have a regression test the moment the fix lands, instead of a vague memory of "we had an issue with refunds once." Start with unordered matching for anything with a reference path you can write down, keep superset out of your safety-critical checks unless you've confirmed it actually catches what you think it catches, and save the LLM judge for the tasks that genuinely don't have one correct answer. None of this needs to be elaborate to be worth more than nothing, which is what most teams are running today.

FAQ

What's the difference between a trajectory and a transcript?

Nothing meaningful. Trajectory, transcript, and trace are used interchangeably across Anthropic's and LangChain's documentation to mean the same thing: the full record of a run, including every tool call, tool result, and reasoning step, not just the final reply.

Should I grade outcomes or trajectories?

Outcomes first, when you can define them. Checking the environment's actual final state is cheaper and harder to fool than any transcript check. Add trajectory grading on top for the failure modes outcome checks can't see, like a duplicate or unsafe tool call that happened to still land on the right final state.

Do I need LangSmith to use AgentEvals?

No. The evaluator functions in the agentevals package run standalone against any list of messages in your own test runner. LangSmith's dataset and client.evaluate workflow is one way to run them at scale against a stored dataset, but it isn't a requirement for the core matching logic.

How many test cases do I actually need to start?

Fewer than you'd guess. Anthropic's own guidance is that 20-50 cases drawn from real failures is a solid starting point, not the few hundred that feels intuitively "enough." Grow the set from whatever breaks in production rather than trying to anticipate everything up front.

Why did my agent's trajectory test pass when there was an obvious bug?

Check your match mode first. superset matching only confirms the reference calls happened; it won't flag an extra or duplicate call layered on top, which is exactly the shape most dangerous bugs take. unordered or strict modes will catch that same case.
