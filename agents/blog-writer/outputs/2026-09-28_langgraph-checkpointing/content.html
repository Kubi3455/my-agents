The first long agent run I lost wasn't taken down by some clever bug. The LLM provider just stopped answering at step four of a five-step research pipeline. The exception bubbled up, my script died, and every search call and summary from steps one through three went with it. All of it had lived in a Python dict in memory. I'd paid for those tokens twice by the end of the afternoon, and that was the week I finally took LangGraph checkpointing seriously.

If you've built anything with LangGraph that runs longer than a few seconds, you've either hit this or you will. APIs time out. Containers get recycled. Someone closes the laptop lid. It's the boring cousin of the multi-agent failures I wrote about when agents get stuck in infinite loops, and honestly it's more common.

Checkpointing is the fix. It's also one of the better-designed parts of the framework. Below is how it actually works, the exact code I used to crash an agent on purpose and bring it back, and the mistakes that cost me the most time.

What LangGraph Checkpointing Actually Saves

A checkpointer is just a storage backend you hand to the graph when you compile it. After every super-step (one "tick" of the graph, where all the nodes scheduled for that tick run), LangGraph writes a snapshot of the entire state to that backend.

Every snapshot. Not just the last one.

That detail is what makes two very different features possible: resuming after a crash, and going back in time to replay an earlier decision. We'll use both.

Threads and the thread_id

Snapshots are grouped by a thread_id that you pass in the config. Think of a thread as one conversation, one job, one article being written. Same thread_id, same history. New thread_id, clean slate.

In practice I just use whatever ID my system already has for the unit of work: a job ID, a ticket number, a user session. Don't invent a second ID scheme just for LangGraph. You'll regret it the first time you need to find a thread at 2 a.m.

What's inside a snapshot

When you call graph.get_state(config) you get a StateSnapshot back. The fields I actually look at day to day:

  • values: the state itself, exactly as your nodes left it
  • next: which node(s) will run next. Empty tuple means the run finished
  • config: includes the checkpoint_id, which is your handle for time travel
  • metadata: things like the step number, handy when you're reading history

If next isn't empty after an exception, you have something to resume. That one check has saved me more debugging time than any logging setup.

Crashing an Agent on Purpose (and Resuming It)

Enough theory. Here's a tiny two-node pipeline: a research step that stands in for an expensive LLM call, and a write step that fails the first time with a fake timeout. I ran this with LangGraph 1.2 and the SQLite checkpointer.

pip install langgraph langgraph-checkpoint-sqlite
import sqlite3
from typing import TypedDict

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.sqlite import SqliteSaver


class State(TypedDict):
    topic: str
    research: str
    draft: str


calls = {"research": 0, "write": 0}
CRASH = {"on": True}


def research(state: State):
    calls["research"] += 1
    print("  research node running (expensive call)")
    return {"research": f"notes about {state['topic']}"}


def write(state: State):
    calls["write"] += 1
    if CRASH["on"]:
        raise ConnectionError("LLM provider timed out")
    return {"draft": f"Draft based on: {state['research']}"}


builder = StateGraph(State)
builder.add_node("research", research)
builder.add_node("write", write)
builder.add_edge(START, "research")
builder.add_edge("research", "write")
builder.add_edge("write", END)

conn = sqlite3.connect("checkpoints.db", check_same_thread=False)
graph = builder.compile(checkpointer=SqliteSaver(conn))
config = {"configurable": {"thread_id": "article-42"}}

# First run: crashes inside "write"
try:
    graph.invoke({"topic": "checkpointing"}, config)
except ConnectionError as e:
    print("crashed:", e)

snap = graph.get_state(config)
print("next:", snap.next)
print("values:", snap.values)

# Provider is back. Resume the SAME thread with None as input.
CRASH["on"] = False
result = graph.invoke(None, config)
print("result:", result)
print("calls:", calls)

And here's what it printed on my machine:

  research node running (expensive call)
crashed: LLM provider timed out
next: ('write',)
values: {'topic': 'checkpointing', 'research': 'notes about checkpointing'}
result: {'topic': 'checkpointing', 'research': 'notes about checkpointing', 'draft': 'Draft based on: notes about checkpointing'}
calls: {'research': 1, 'write': 2}

Look at the last line. research ran once. The expensive part didn't repeat. Only the node that actually failed ran again.

The line that trips people up is graph.invoke(None, config). Passing None as the input feels wrong the first time you see it. What it means is: don't start a new run, pick up this thread from its latest checkpoint and keep going. Pass a real input instead and you're starting a fresh run on top of the saved state, which is a different thing entirely.

Quick aside: the same pattern works when the "crash" is a local model choking under load. If you're running agents against Ollama like in my guide to connecting local LLMs with web search, timeouts on a busy laptop are pretty much guaranteed, so this is worth wiring in early.

InMemorySaver vs SqliteSaver vs PostgresSaver

LangGraph ships a few checkpointers, and the choice matters more than it looks. The short version:

My honest take: skip InMemorySaver for anything you'll run more than once. It looks like persistence, it behaves like persistence in your tests, and then the process restarts and everything is gone. I'd start with SQLite on day one. It's a single file, you can open it with any SQLite browser, and moving to Postgres later is mostly a one-line change.

One thing to remember with Postgres: call checkpointer.setup() once so it creates its tables. The official LangGraph persistence docs cover the connection details, and the SQLite package lives on PyPI as langgraph-checkpoint-sqlite.

Durability Modes: How Often LangGraph Writes to Disk

This is the part almost nobody mentions, and it changes what "resumable" really means. You can pass durability to invoke or stream, with three options:

  • "sync" writes each checkpoint before the next step starts. Safest, slowest.
  • "async" writes while the next step is already running. Faster, with a small window where a hard crash can lose the latest checkpoint. This is the default.
  • "exit" only writes when the graph exits, whether it finished, errored, or hit an interrupt.

I wanted to see the difference for myself, so I ran the same crashing graph once per mode and counted the saved checkpoints:

sync  -> next=('nb',) a='done' checkpoints=3
async -> next=('nb',) a='done' checkpoints=3
exit  -> next=('nb',) a='done' checkpoints=1

Interesting, right? With a normal Python exception, all three modes could resume, because "exit" still saves on the way out. What "exit" threw away was the history. One checkpoint instead of three means no time travel.

And a raised exception is the friendly case. If the process gets killed outright (out-of-memory, a container restart, a power cut), there's no "on the way out." The durable execution docs say it plainly: with "exit", intermediate state isn't saved, so you can't recover from a crash mid-run. My rule: "sync" for anything that costs real money per step, the default "async" for everything else, and "exit" only for short graphs where speed genuinely matters.

Time Travel: Replaying and Forking an Old Checkpoint

Because every super-step is saved, you can walk back through a thread's history, pick an older checkpoint, change the state, and run forward from there. It's the closest thing to a debugger that agents have.

from typing import TypedDict

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver


class S(TypedDict):
    n: int


def inc(s: S):
    return {"n": s["n"] + 1}


b = StateGraph(S)
b.add_node("inc", inc)
b.add_edge(START, "inc")
b.add_edge("inc", END)
g = b.compile(checkpointer=InMemorySaver())

cfg = {"configurable": {"thread_id": "t1"}}
g.invoke({"n": 0}, cfg)

# Find the checkpoint right before "inc" ran
history = list(g.get_state_history(cfg))
before_inc = next(h for h in history if h.next == ("inc",))

# Fork it with different state, then run forward from the fork
forked = g.update_state(before_inc.config, {"n": 100})
print(g.invoke(None, forked))  # {'n': 101}

Where this really pays off is debugging a bad decision deep inside a run. Say your router picked the wrong agent at step 7. Instead of rerunning all seven steps and hoping it happens again, you fork step 6, tweak the state, and watch what the router does. I use this constantly when debugging multi-agent workflows in CrewAI and LangGraph. The time travel guide has more patterns.

Checkpointing is also what makes interrupts work. If you want an agent to pause and wait for a person to approve something, that pause has to be stored somewhere, which is exactly what the checkpointer does. I went deeper on that in human-in-the-loop for AI workflows.

Common Pitfalls With LangGraph Checkpointing

Forgetting the thread_id

Compile with a checkpointer, call invoke without a config, and you get this:

ValueError: Checkpointer requires one or more of the following 'configurable' keys: thread_id, checkpoint_ns, checkpoint_id

At least it's loud. Annoying in a notebook, but I'd rather have that than silent state loss.

Sharing a SQLite connection across threads

Plain sqlite3.connect() refuses to be used from a different thread than the one that created it. The moment your graph runs inside a web server or a thread pool, you'll see:

ProgrammingError: SQLite objects created in a thread can only be used in that same thread.

That's why the example above uses check_same_thread=False. It's fine for light use. If you have real concurrency, that's your signal to move to AsyncSqliteSaver or Postgres, not to pile on locks.

Side effects that run twice

Look back at the crash demo: write ran twice. That was harmless there. Now imagine the node sends an email, then crashes on the line after. On resume, the whole node runs again, and your customer gets two emails.

Checkpoints are saved between steps, not inside them. So I keep each side effect in its own small node, and I make those nodes idempotent where I can (an idempotency key on the API call, or a "did I already send this?" check). The same thinking applies to retries in general, which I covered in practical retry and exit strategies for AI agents.

Reusing a thread_id by accident

If you invoke a finished thread with fresh input, LangGraph doesn't start from zero. It starts from that thread's saved state. With a message list, that means yesterday's conversation quietly leaks into today's run. Use a new thread_id per job unless you actually want continuity.

When Checkpointing Isn't Enough

I like this feature a lot, but it has limits worth knowing before you lean on it:

  • It doesn't make LLMs deterministic. Resume or replay a step and the model can give a different answer.
  • It doesn't detect crashes for you. Something still has to notice the failed run and call invoke(None, config). A cron job, a queue worker, a retry wrapper.
  • Storage grows. Every super-step is a row. Long-running threads add up, so plan some cleanup.
  • Short-term state only. The checkpointer is per-thread. Long-term memory shared across threads belongs in a separate store.

If you're still deciding between frameworks, this is one area where LangGraph is noticeably ahead in my experience. My AutoGPT vs CrewAI vs LangGraph comparison goes into the trade-offs.

Conclusion

If I were starting a LangGraph project today, here's what I'd do before writing a single prompt: SqliteSaver from day one, thread_id set to the job ID I already have, durability="sync" on anything that burns paid tokens, and one side effect per node.

That's maybe fifteen minutes of setup. LangGraph checkpointing won't make your agent smarter, but it means the next timeout costs you one step instead of the whole run. Try the crash demo above with your own graph. Break it on purpose once, and you'll trust it a lot more when it breaks for real.

FAQ

How do I resume a LangGraph agent after a crash?

Call graph.invoke(None, config) with the same thread_id as the failed run. LangGraph loads the latest checkpoint and continues from the node that didn't finish.

Does resuming re-run nodes that already finished?

No. Nodes completed in earlier super-steps are skipped. The node that failed runs again from the start, which is why side effects inside it should be idempotent.

Can I use LangGraph checkpointing without a database?

Yes, with InMemorySaver, but everything disappears when the process stops. For anything beyond tests, SQLite is the lightest option that actually survives a restart.

What's the difference between a checkpointer and a store in LangGraph?

A checkpointer saves the state of one thread step by step. A store holds long-term memory that different threads can share, like user preferences. Most real apps end up using both.
