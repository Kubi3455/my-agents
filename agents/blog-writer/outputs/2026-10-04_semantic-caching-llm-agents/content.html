Last week I decided to bolt semantic caching for LLM agents onto a pipeline that was asking a model the same handful of questions a few hundred times a day, and the caching library ate more of my afternoon than the agent itself ever had. pip install gptcache finishes in four seconds and gives you almost nothing: no embedding model, no vector store, no ONNX runtime. The first time you call cache.init(), it tries to quietly pip-install the rest for you, mid-script, and if that silent install fails or lands in the wrong environment, you get a stack trace three layers deep in someone else's lazy-import code. Not fun at 4pm on a Friday.

If you've ever added a caching layer to an agent and watched it do nothing, or worse, hand back a confidently wrong answer to a question that only sounded like one you'd cached, you already know why semantic caching is more interesting than it looks on a slide. Exact-match caching barely helps agents, because agents rarely ask the exact same thing twice. They ask "what's the refund policy" and then, three tool calls later, "can I get money back on this," and a dumb cache sees two different strings. It's the same kind of blind spot I ran into while debugging infinite loops in CrewAI and LangGraph: the symptom looks new, but the root cause is just agents repeating themselves.

Here's what I'll actually walk through: how semantic caching tells those two questions apart from a genuinely different one, the GPTCache setup that works once you know which three packages it forgot to mention, where Redis's managed LangCache fits if you don't want to run that infrastructure yourself, and the one tuning knob that decides whether your cache saves money or quietly lies to users.

Why agents keep paying for the same question twice

A chatbot gets one phrasing of a question from one user. An agent pipeline multiplies that problem in two directions at once. First, you've usually got more than one user asking variations of the same thing — "how do I reset my password" and "I'm locked out, help" are the same support ticket wearing different words. Second, agents ask themselves near-duplicate questions across a run: a planner re-checking "what tools are available" after every step, a retriever re-summarizing the same document chunk for three different sub-tasks. Same repetitive pattern, just expensive instead of broken.

None of that shows up as a single expensive call you can profile and fix. It shows up as a thousand small, slightly-different calls, each one too cheap to notice until the bill arrives. The GPT Semantic Cache paper measured this directly against a production-style workload and found cache hit rates of 61.6–68.8% once a semantic layer was in front of the model, meaning roughly two-thirds of the calls were paying for an answer the system already had. That's real money.

It compounds with problems I've written about before, too. If you're fanning out agent calls fast enough to hit provider rate limits, a chunk of that volume is often the same question asked five different ways by five different workers. And if your tool definitions are already eating a third of your context window before the real request even starts, every one of those redundant calls is paying that tax again on top of the API cost. Semantic caching doesn't fix either of those problems directly, but it quietly shrinks how often you hit them, because a cache hit never reaches the rate limiter at all.

How semantic caching for LLM agents decides "close enough"

A regular cache is a dictionary: same key in, same value out, nothing in between. Semantic caching replaces the key with a vector. The incoming prompt gets converted to an embedding, that embedding gets compared against every embedding already in the cache using cosine similarity, and if the closest match clears a threshold, you get the stored answer back instead of a model call. Miss, and the real call goes out. Then both the question and the answer get stored for next time.

The threshold is the whole game. Redis, whose LangCache product exists specifically to run this step for you, documents a default similarity threshold of 0.85 with a recommended starting range of 0.8–0.9, and is upfront about the tradeoff: tighter means fewer wrong answers and more real LLM calls, looser means a higher hit rate and more risk of returning the answer to a different question that merely sounds similar. There's no universally correct number. A support FAQ bot can run loose. A bot answering account-specific billing questions can't.

Here's the confusing part if you're coming from exact-key caching: a "hit" in a semantic cache isn't a correctness guarantee anymore, it's a bet. You're trading some chance of a wrong answer for a lot fewer model calls. That trade is usually worth it. But only if you've set the threshold on purpose, not just kept whatever default your library shipped with.

Setting up GPTCache (and the three packages it won't tell you about)

GPTCache is the open-source option if you want this running locally without a managed service. The documented quickstart looks like four lines. In practice, I needed onnxruntime, transformers, sqlalchemy, and faiss-cpu installed up front, because GPTCache's own lazy-install mechanism tried to shell out to pip mid-import and didn't reliably land the packages in my virtualenv. Install them yourself first and the rest goes smoothly:

pip install gptcache onnxruntime faiss-cpu sqlalchemy
pip install "transformers==4.36.2" "tokenizers<0.20"

That second pin matters more than it looks. GPTCache's bundled ONNX embedding wrapper calls a tokenizer method, encode_plus, that current transformers releases have quietly dropped from the fast-tokenizer path. Install whatever's newest and you'll get an AttributeError two layers down in a vendored dependency, nowhere near your own code. I lost a chunk of the afternoon to that one. Pinning an older version fixed it.

With those installed, the actual cache setup is short:

from gptcache import cache
from gptcache.adapter.api import put, get
from gptcache.processor.pre import get_prompt
from gptcache.embedding import Onnx
from gptcache.manager import CacheBase, VectorBase, get_data_manager
from gptcache.similarity_evaluation.distance import SearchDistanceEvaluation

onnx = Onnx()
data_manager = get_data_manager(
    CacheBase("sqlite"),
    VectorBase("faiss", dimension=onnx.dimension),
)

cache.init(
    embedding_func=onnx.to_embeddings,
    data_manager=data_manager,
    similarity_evaluation=SearchDistanceEvaluation(),
    pre_embedding_func=get_prompt,  # required for plain put()/get() strings
)

put("How do I reset my password?", "Go to Settings > Security > Reset Password.")

get("How do I change my password?")   # -> the cached answer
get("What's the weather in Tokyo?")   # -> None, correctly treated as a miss

I ran exactly that against both a paraphrased password question and an unrelated one. The paraphrase came back with the cached answer; the weather question came back None, which is the result you want, a clean miss rather than a false match. That pre_embedding_func=get_prompt line isn't optional window dressing either: skip it and put() assumes you're passing OpenAI-style chat messages, not a plain string, and throws a TypeError that has nothing to do with your actual mistake. GPTCache's own adapter wraps openai.ChatCompletion.create directly if you'd rather cache real completions instead of calling put/get by hand, but the manual version above is what I'd reach for first just to prove the similarity matching behaves the way you expect before you wire it into a live pipeline.

GPTCache vs. a managed option like Redis LangCache

GPTCache gets you running for free on a laptop, but you're now the one operating a vector store, an embedding model, and a SQLite file that needs to survive restarts. Redis LangCache takes the opposite bet: you call a REST API with a cacheId, pick an embedding provider (Redis's own, OpenAI, or your own), and it handles the embedding, storage, and similarity search behind that one endpoint. Redis's own numbers put cost reduction as high as 73–90% on high-repetition workloads, with roughly a 15x latency improvement on cache hits versus a full model round trip, which lines up with the hit-rate numbers from the GPTCache paper above — a cache hit is just a vector lookup, and vector lookups are fast.

Pros of GPTCache

  • Free, runs entirely on your own infrastructure, nothing leaves your network
  • Swappable pieces: SQLite or a real database, FAISS or Milvus, ONNX or OpenAI embeddings
  • No per-call pricing on top of what you're already paying the model provider

Cons of GPTCache

  • Dependency pinning is on you, and the project's lazy-install path can't be trusted blindly
  • You own uptime, backups, and scaling the vector store as cache size grows
  • No managed dashboard for hit rate or threshold tuning; you build that yourself

Where a cache hit becomes a wrong answer

Every semantic cache can return a response to a question that isn't quite the one that was asked, because similarity isn't equivalence. "Can I cancel my subscription" and "can I cancel my order" sit close together in embedding space if your corpus doesn't have much else nearby, and a loose threshold will happily merge them. You'll skip the real model call. You won't skip the embarrassment when a customer gets billing advice for the wrong product.

I'd treat the threshold as something you tune with real traffic, not something you set once and forget. Start tight, around 0.9, log what gets rejected as a near-miss, and loosen gradually while spot-checking the matches that start sneaking through. Start loose instead, and you've already shipped wrong answers before you notice the pattern. By then the damage is done.

Staleness is the other failure mode nobody mentions until it bites them. A cached answer about "current pricing" is correct right up until pricing changes, and a similarity-based cache has no idea that happened. If what you're caching can go stale, pair the similarity threshold with a TTL, or scope entries to an attribute (a product version, a pricing tier) you can invalidate in bulk when the underlying fact changes.

Common Pitfalls

  • Trusting GPTCache's lazy pip installs. Pre-install onnxruntime, transformers (pinned), sqlalchemy, and faiss-cpu yourself rather than letting a mid-import subprocess.check_call do it for you.
  • Forgetting pre_embedding_func=get_prompt. Without it, plain-string put()/get() calls assume a chat-message dict and fail with an unrelated TypeError.
  • Never tuning the default threshold. Whatever a library ships as default is a guess about your traffic, not a fact about it.
  • Caching answers that go stale. Add a TTL or attribute-based invalidation for anything tied to a fact that changes (pricing, inventory, policy).
  • Measuring only cost, not correctness. A high hit rate with no spot-checking just means you're confidently wrong more often, faster.

When semantic caching alone isn't enough

Semantic caching cuts repeated questions, not every expensive pattern an agent produces. If your real problem is that agent memory keeps re-fetching context it already has, a cache sitting in front of the model doesn't fix a retrieval design issue upstream of it; it just makes the symptom cheaper. And a cache hit is invisible in a log line the same way everything else about agent behavior is — if you can't already see which calls your agents are actually making, you won't be able to tell whether your cache is saving money or quietly serving stale answers to real traffic. Wire up tracing first, or at least alongside, so a cache hit rate of 70% means something you can verify instead of a number you're trusting on faith.

Conclusion

If I were adding this to a new agent pipeline today, I'd start with GPTCache locally just to watch the hit rate on real traffic for a week, pre-installing the dependencies above so I wasn't debugging someone else's lazy-import code. Once the threshold was dialed in and the cost savings were real instead of theoretical, that's the point where I'd weigh Redis LangCache against the ops cost of running the vector store myself. Either way, don't skip the step where you actually look at what the cache is matching. Check it by hand. A cache that saves money by being occasionally, invisibly wrong isn't a win. It's a cost you've moved somewhere you can't see it yet.

FAQ

Is semantic caching the same thing as prompt caching?

No, and mixing them up costs you debugging time. Prompt caching (what Anthropic and OpenAI offer natively) reuses the processed tokens of an identical prompt prefix. Semantic caching matches on meaning across different prompts entirely, using embeddings and a similarity threshold, and it's typically a separate layer you add yourself rather than a provider API flag.

What similarity threshold should I start with?

Redis LangCache's documented default is 0.85, with a recommended range of 0.8–0.9. I'd start at the tight end of that range, around 0.9, and loosen it only after watching what real queries match at that setting.

Does semantic caching help with rate limits too?

Indirectly. A cache hit never reaches the model provider at all, so it can't trigger a 429. It won't fix a pipeline that's already fanning out too many concurrent calls for genuinely new questions; that's a separate problem with its own fix. But it does shrink the total volume hitting that limit in the first place.

Can a semantic cache return a wrong answer?

Yes, by design. A similarity match above the threshold isn't a guarantee of an identical question, just a bet that it's close enough. That's the entire tradeoff versus exact-key caching: more hits, at the cost of occasionally merging two questions that only sound alike.

Do I need this for a small side project?

Probably not yet. If your agent makes a few dozen calls a day, the dependency wrangling above costs more time than the caching saves. Once you're seeing the same questions recur across users, or an agent re-asking itself the same thing across steps in a loop, that's the signal it's worth the setup.
